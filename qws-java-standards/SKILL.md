# QWS Java 开发规范

在用户指定的 Java 开发范围内应用以下规范；检查任务仅报告问题，除非用户要求修复。规则来源为用户提供的《代码格式标准》，保留其优先级和例外，不将推荐用法解释成无条件禁令。

## 开始前

- 阅读适用的项目说明和构建配置，确认目标 Java 版本以及 Commons Lang、Hutool、Guava 和 `com.guming.api.json.JsonUtil` 的实际可用性。可执行命令时查询 `java -version`；编译兼容性以 Maven/Gradle 的 release、source/target 或 toolchain 配置为准，不能仅以本机 JDK 为准。
- 在项目目标 Java 版本支持的范围内优先使用现代 API，同时遵守下面明确指定的用法。
- 先查找项目已有的常量、枚举和相关实现；只调整本次任务涉及的代码，不为了统一风格批量改动无关文件。
- 不生成缺少依赖的 import。所需库不可用时，遵循项目依赖管理约定；只有任务允许且确有必要时才增加依赖，并沿用项目管理的版本。不宜增加依赖时使用语义等价的现有工具或 JDK 写法，并在交付时简述偏离规范的原因。

## 规范分类

规则编号对应原文条款编号，按用途分组，便于检查结果追溯到来源。

| 分类 | 规则 |
| --- | --- |
| 工具类与对象创建 | R1 判空、R2 集合创建、R7 JSON 处理 |
| 代码结构与引用 | R3 花括号、R6 import |
| 数据校验与业务值 | R4 校验位置、R5 常量与枚举 |
| 迭代与改动范围 | R8 代码复用、R9 限制重构范围 |

## 一、工具类与对象创建

### R1：优先使用封装好的空值判断方法

- 对象判空：优先使用 `java.util.Objects.isNull(value)` / `Objects.nonNull(value)`。
- 字符串判空：优先使用 `org.apache.commons.lang3.StringUtils.isBlank(value)` / `StringUtils.isNotBlank(value)`。
- 集合判空：优先使用 `cn.hutool.core.collection.CollectionUtil.isEmpty(values)` / `CollectionUtil.isNotEmpty(values)`。
- 按值的实际类型和业务语义选方法。`isBlank` 会同时处理 null、空字符串和纯空白字符串，集合 `isEmpty` 会同时处理 null 和空集合；若业务需要区分这些状态，保留必要的区分，不机械替换而改变行为。

### R2：常规集合使用 Guava 工厂方法

使用 `com.google.common.collect` 下的以下方法创建常规集合：

- List：`Lists.newArrayList()`。
- Set：`Sets.newHashSet()`。
- Map：`Maps.newHashMap()`。

存在特殊要求时选择满足要求的实现或工厂方法，例如线程安全、排序、插入顺序、不可变性或特定容量。不要将 `ConcurrentHashMap`、`TreeMap` 等特殊集合机械替换为普通集合。

### R7：JSON 处理优先使用项目封装

优先使用 `com.guming.api.json.JsonUtil` 中封装好的方法：

- 对象转 JSON 字符串：`JsonUtil.toJson()`。
- JSON 字符串转对象：按目标类型选择 `JsonUtil.of()`、`JsonUtil.ofList()` 或 `JsonUtil.ofMap()`。

上述名称表示方法选择，不表示这些方法都是无参方法。调用前通过项目源码、已有调用或依赖 API 确认实际参数、重载、泛型和返回类型，不猜测内部工具类的签名或所属依赖坐标。已有封装能满足需求时，不另起一套 JSON 工具类或直接改用其他 JSON 库。

确认封装是否支持当前数据结构，并保持任务需要的字段映射、空值、日期格式和异常处理语义。工具类不可用或确实无法满足需求时，按“开始前”的依赖与例外处理约定执行，并说明原因。

## 二、代码结构与引用

### R3：if 分支使用花括号

`if`、`else if` 和 `else` 的分支体都使用 `{}`，包括仅有一条语句的情况。不输出省略花括号的单行分支。

### R6：优先通过 import 引入类

使用普通 `import` 引入类，正文使用类的简单名称。只有存在无法同时导入的同名类冲突时，才在必要位置使用类的全限定名；不要为规避导包而普遍内联完整包名。

## 三、数据校验与业务值

### R4：避免多余的数据校验

数据完整性和格式正确性的校验通常放在数据保存或生成阶段。在已有明确数据契约、上游已完成校验的内部使用处，不重复增加相同的检查。

外部提供的数据等特殊情况应保留必要校验。先确认数据来源和已有校验保障，不能仅凭“减少判断”删除业务分支、必要的空值处理或边界校验，也不能假定未经确认的数据已经有效。

### R5：避免魔法值，优先复用常量和枚举

对具有业务含义的状态码、类型标识、阈值和字符串等，优先复用现有常量或枚举。现有定义不能满足需求时，在合适的业务归属位置新增常量或枚举，名称应表达实际含义。

不要重复定义已有概念，也不要把每个无歧义的普通字面量都机械提取成常量。

## 四、迭代与改动范围

### R8：迭代旧功能优先复用已有代码

先查找旧功能的入口、调用链、已有方法、模型和相关测试，尽可能在既有实现上增加本次迭代内容。已有代码能满足需求时直接复用，避免复制相同逻辑或另建一套平行实现。

复用以适配实际需求和保持正确行为为前提，不为勉强复用而引入不相关的分支，也不借复用之名进行本次任务不需要的大规模抽象或改写。

### R9：控制迭代范围，不擅自重构

围绕用户本次需求实施必要改动。除非遇到比较严重的问题，不扩大迭代范围，不自作主张重构已有代码；风格偏好、顺手清理、统一写法或追求更现代的 API 本身不是扩大范围的理由。

若发现比较严重的问题，例如会使本次功能无法正确运行、造成数据错误或存在明确安全缺陷，应说明具体证据、影响和最小必要修复范围。在已有授权范围内处理；若需要明显扩大任务范围，先说明并取得用户确认，不能仅凭“严重”标签无限扩大重构。

用户明确要求的重构属于本次任务范围，仍应遵守该范围并优先保留可复用的实现。

## 完成前

- 针对本次生成或修改的代码检查四类规范中的 R1–R9：确认工具方法和 JSON 调用真实可用、数据语义正确、代码结构与业务值符合要求，且复用了适用的已有实现，没有无依据地扩大改动范围。
- 在项目环境允许时运行与改动相称的编译或现有检查；说明实际执行的验证，不把未执行的检查报告为通过。
- 正常开发任务简述改动与验证结果；仅在存在例外或限制时补充原因，不必每次输出完整规范清单。
- 按规范检查代码时，给出位置、规则编号、问题及建议；将项目约束导致的合理例外与实际违规区分开。
